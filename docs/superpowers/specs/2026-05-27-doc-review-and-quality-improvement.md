# 文档审查与质量改进方案

## 1. 背景与问题

### 1.1 现象

1. **文档审查缺乏系统化机制**
   - 缺少专门的文档审查skill
   - 环境准备（keys、接口、依赖等）容易被忽略
   - 文档质量无法快速定位问题

2. **实施计划缺乏阶段划分**
   - 计划没有明确的阶段结构
   - 环境准备阶段经常被跳过
   - 开发者直接进入业务代码实现，导致环境问题频发

3. **自测和单元测试质量不足**
   - 自测过于简单，只是简单测试
   - 单元测试覆盖不足，无法做到全覆盖
   - Leader审查缺乏系统化的协调机制

### 1.2 根因

| 原因 | 说明 |
|------|------|
| 缺少专用skill | 没有专门的文档审查skill，文档审查依赖人工经验 |
| 计划模板缺失 | 没有强制要求分阶段的计划模板 |
| 测试标准不明确 | 缺少明确的测试覆盖率和质量标准 |
| 审查协调缺失 | Leader审查没有系统化的协调机制 |

### 1.3 设计立场

- **文档审查必须系统化**：通过skill实现标准化的文档审查流程
- **环境准备必须优先**：所有实施计划的第一阶段必须是环境准备
- **自测必须严格**：代码评审和测试运行必须同时进行
- **审查必须独立**：Leader必须调用独立的审查skill进行验证

---

## 2. 目标与非目标

### 2.1 目标

1. 创建文档审查skill，支持多种文档类型的审查，特别关注环境准备
2. 修改计划模板，强制要求分阶段计划，第一阶段必须是环境准备
3. 创建自测skill，建立明确的测试覆盖标准
4. 建立Leader审查协调机制，确保调用 `requesting-code-review` skill

### 2.2 非目标

- 不修改现有的核心路由逻辑
- 不改变现有的skill三层存储体系
- 不影响现有的产物类型定义

## 3. 核心设计

### 3.1 文档审查Skill设计

#### 3.1.1 文件夹结构

```
.cursor/skills/document-review/
├── SKILL.md                    # 主入口，包含通用审查流程
├── review-rules/               # 审查规则库（按需加载）
│   ├── spec.md                 # 规格/需求文档审查规则
│   ├── design.md               # 架构/技术设计文档审查规则（含环境准备）
│   └── plan.md                 # 实施计划审查规则
└── checklists/                 # 检查清单模板
    └── review-checklist.md     # 通用审查检查清单
```

#### 3.1.2 按需加载机制

主 `SKILL.md` 包含通用审查流程和文档类型识别逻辑，根据文档类型动态加载对应的 `review-rules/*.md`。

**文档类型识别**：

| 文档特征 | 类型 | 加载规则文件 |
|---------|------|-------------|
| 包含"需求"、"用户故事"、"功能"、"spec" | 规格/需求文档 | `spec.md` |
| 包含"架构"、"设计"、"实现"、"API"、"环境"、"部署" | 架构/技术设计文档 | `design.md` |
| 包含"计划"、"plan"、"任务"、"阶段" | 实施计划文档 | `plan.md` |

#### 3.1.3 设计文档审查规则（含环境准备）

**架构/技术设计文档必须检查项**：

1. **整体设计**
   - 架构图清晰，组件职责明确
   - 接口定义完整，依赖关系清晰
   - 设计模式合理，可扩展性好

2. **环境准备（重点）**
   - 依赖管理：列出所有第三方依赖及版本、安装命令、锁文件
   - 环境变量：列出所有必需变量、提供 .env.example、说明密钥获取方式
   - 外部服务：列出所有服务依赖、提供 Docker Compose 等本地方案
   - 开发环境：明确运行环境要求、提供环境验证命令
   - 测试环境：测试数据库、Mock 服务、测试数据准备

3. **技术细节**
   - API 设计：接口定义、请求/响应格式、错误码
   - 数据库设计：表结构、索引、迁移方案
   - 安全考虑：认证授权、数据加密、输入验证

### 3.2 分阶段计划设计

#### 3.2.1 计划阶段结构

所有实施计划必须明确划分阶段，第一阶段必须是环境准备：

```markdown

## Phase 1: 环境准备与验证

**目标：** 搭建完整的开发环境，确保所有依赖和配置就绪

**验证标准：** 环境验证命令全部通过，可以开始业务开发

### Task 1.1: 依赖安装与配置
[具体步骤...]

### Task 1.2: 环境变量配置
[具体步骤...]

### Task 1.3: 外部服务配置
[具体步骤...]

### Task 1.4: 开发环境验证
[具体步骤...]

---

## Phase 2: 核心功能实现

**目标：** 实现核心业务逻辑

**验证标准：** 所有核心功能测试通过

[具体任务...]

---

## Phase 3: 集成与优化

**目标：** 集成各模块，优化性能和用户体验

**验证标准：** 集成测试通过，性能达标

[具体任务...]
```

#### 3.2.2 环境准备完成标准

**必须通过项**（全部通过才能进入Phase 2）：

1. **依赖安装验证**
   - `npm install` 或 `pip install` 成功
   - 无版本冲突警告
   - 所有依赖版本符合要求

2. **环境变量验证**
   - `.env` 文件存在且包含所有必需变量
   - 环境变量加载测试通过
   - 敏感信息未提交到版本控制

3. **服务连接验证**
   - 数据库连接成功
   - 缓存服务连接成功（如使用）
   - 消息队列连接成功（如使用）
   - 第三方API连接成功（如使用）

4. **开发工具验证**
   - 代码编辑器配置正确
   - 调试工具可用
   - 热重载功能正常

5. **测试环境验证**
   - 测试数据库配置正确
   - 测试框架可用
   - 测试数据准备就绪

### 3.3 自测和单元测试改进

#### 3.3.1 自测Skill设计

**文件夹结构**：

```
.cursor/skills/self-review/
├── SKILL.md                    # 主入口，包含自测流程
├── review-checklists/          # 审查检查清单
│   ├── code-quality.md         # 代码质量检查清单
│   ├── test-coverage.md        # 测试覆盖检查清单
│   ├── security-check.md       # 安全检查清单
│   └── performance-check.md    # 性能检查清单
├── test-templates/             # 测试模板
│   ├── unit-test-template.md   # 单元测试模板
│   ├── integration-test.md     # 集成测试模板
│   └── e2e-test-template.md    # 端到端测试模板
└── examples/                   # 示例
    ├── good-test.md            # 优秀测试示例
    └── bad-test.md             # 有问题测试示例
```

#### 3.3.2 自测流程

1. **代码质量评审**
   - 代码规范检查
   - 设计模式检查
   - 错误处理检查

2. **测试覆盖评审**
   - 单元测试覆盖
   - 集成测试覆盖
   - 测试质量评估

3. **功能验证**
   - 正常流程测试
   - 异常流程测试
   - 性能测试

4. **安全检查**
   - 输入验证
   - 认证授权
   - 数据保护

#### 3.3.3 单元测试覆盖标准

**覆盖率要求**：

| 指标 | 最低要求 |
|------|---------|
| 语句覆盖率 | ≥ 80% |
| 分支覆盖率 | ≥ 75% |
| 函数覆盖率 | ≥ 90% |
| 行覆盖率 | ≥ 80% |

**模块覆盖率要求**：

| 模块类型 | 覆盖率要求 |
|---------|-----------|
| 核心业务逻辑 | 100% |
| 工具函数 | 100% |
| API端点 | 90% |
| 数据访问层 | 85% |
| UI组件 | 70% |

**必须测试的场景**：

1. **正常流程**
   - 主要功能正常工作
   - 标准输入输出
   - 预期使用场景

2. **边界条件**
   - 空值处理
   - 极值处理
   - 类型转换
   - 数组边界

3. **错误处理**
   - 无效输入
   - 网络错误
   - 权限错误
   - 资源不足

4. **并发场景**
   - 竞态条件
   - 死锁预防
   - 资源锁
   - 会话管理

### 3.4 Leader审查协调机制

#### 3.4.1 审查协调流程

1. **自测结果验证**
   - 验证自测报告完整性
   - 检查自测覆盖率是否达标
   - 确认自测问题已修复

2. **代码审查协调**
   - 准备审查上下文（git SHAs）
   - 调用 `requesting-code-review` skill
   - 处理审查反馈

3. **独立审查验证**
   - 确保审查者独立性
   - 覆盖所有变更文件
   - 评估五个维度：正确性、可读性、架构、安全、性能

4. **审查结果整合**
   - 整合多个审查者的反馈
   - 优先级排序
   - 分配修复任务
   - 验证修复结果

#### 3.4.2 审查频率要求

- **每个WU完成后**：必须进行代码审查
- **每个Phase完成后**：必须进行阶段审查
- **最终合并前**：必须进行最终审查

#### 3.4.3 审查质量要求

- **审查独立性**：审查者不能是实现者
- **审查全面性**：必须覆盖所有变更文件
- **审查及时性**：审查必须在24小时内完成
- **审查有效性**：审查问题必须得到修复
