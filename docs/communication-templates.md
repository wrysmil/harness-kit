# 技术负责人沟通话术模板

> **目的**：帮助产品经理/项目经理与技术负责人进行专业、清晰的需求沟通，确保技术负责人准确理解需求并按照规范执行。

---

## 一、需求沟通话术

### 1.1 初次需求沟通（高层级）

**场景**：首次向技术负责人介绍新功能或改进需求。

**话术模板**：

```
【需求背景】
我们需要在 [具体模块/功能] 中引入 [具体改进/新功能]，以解决 [具体问题/痛点]。

【核心目标】
1. [目标1]：[具体描述，可衡量]
2. [目标2]：[具体描述，可衡量]
3. [目标3]：[具体描述，可衡量]

【关键约束】
- 时间约束：[具体时间要求]
- 技术约束：[具体技术限制]
- 资源约束：[具体资源限制]

【期望产出】
请提供：
1. 技术方案概述（1-2页）
2. 风险评估与缓解措施
3. 初步工作量估算
4. 需要确认的开放问题清单
```

**示例**（基于Coder角色设计）：

```
【需求背景】
我们需要在Cursor编排中引入Coder角色，以解决当前Implementer角色在代码类任务中缺乏完整交付闭环的问题。

【核心目标】
1. 为代码类WU引入"资深开发者"职责：实现 + 单测 + 自测 + 开发者自检（硬门槛）
2. 保持Leader的定位为"技术主管/编排者"：与用户交互、拆WU、资料传递、整合与验证
3. 强化Leader的"对甲方汇报"能力：提供阶段性进展、风险与变更沟通、验收口径

【关键约束】
- 时间约束：2周内完成设计评审
- 技术约束：不改变Harness的阶段门禁
- 资源约束：不影响现有角色分工

【期望产出】
请提供：
1. Coder角色详细设计文档
2. 与现有角色（Implementer、Reviewer）的边界定义
3. 验证命令与测试策略
4. 需要确认的开放问题清单
```

### 1.2 详细需求说明（具体任务）

**场景**：向技术负责人详细说明具体任务要求。

**话术模板（委派子 Agent 时用，简练）**：

```
WU-<id>：<名称> · role / wu_type · 遵循 agents/<role>.md

目标：…
Done：- [ ] …
可改：`a.ts`, `b.ts`
禁：WU 外；commit/push；.env
Skills：<slug> → SKILL 路径
验证：`npm test -- …`
cwd：<worktree_path>   # 仅沙箱批次；否则不写

返回：见 agents/<role>.md § 返回格式
```

**勿**在 prompt 里复述 agent 正文中的工程化闭环、自检字段说明；细节以 `agents/coder.md` 等为准。

**示例**（基于Coder角色设计）：

```
【任务标识】
WU-01：实现Coder角色基础框架

【任务目标】
创建Coder角色的详细设计文档和基础实现框架，确保能够处理代码类WU的完整交付闭环。

【验收标准】（缺一不可）
- [ ] 角色职责明确定义：资深开发者，对WU质量闭环负责
- [ ] 验证命令可执行：至少包含单测运行
- [ ] 开发者自检机制：self_check字段必须为PASS才能报完成
- [ ] 与现有角色边界清晰：不重规划、不派子Agent、不修改允许范围外文件

【允许修改范围】
仅限以下文件（路径完整）：
- `harness-kit/core/orchestration/agents/coder.md`
- `harness-kit/.agents/agents/coder.md`
- `harness-kit/docs/superpowers/specs/2026-05-26-coder-role-design.md`

【禁止行为】
- 禁止修改：`harness-kit/core/**`
- 禁止新增依赖（除非明确要求）
- 禁止Git commit/push（除非明确要求）
- 禁止访问`.env`与密钥路径

【工程化要求】
1. 日志：关键路径、错误分支有结构化日志
2. 错误处理：对外边界失败可观测、可诊断
3. 单测：新增/变更逻辑须有单测
4. 自测：实际运行验证命令，禁止未运行就写pass

【验证命令】
必须执行并回报结果：
```bash
# 运行Coder角色相关测试
npm test -- harness-kit/.agents/agents/coder.md.test.ts
```

【上下文资料】
- Spec：`harness-kit/docs/superpowers/specs/2026-05-26-coder-role-design.md` — § 角色与职责边界
- Plan：`harness-kit/docs/superpowers/specs/2026-05-26-coder-role-design.md` — § 需要的变更清单
- 编码规范：`harness-kit/project.profile.md`

【返回格式】
必须包含：
1. 变更摘要（文件路径 + 说明）
2. 测试资产（文件路径 + 说明）
3. 验证结果（命令 + 结果 + 输出摘要）
4. 开发者自检（含 code_review）
5. 完成状态（wu_status: done/blocked）
6. Skills使用（已加载 + 已跳过）
7. 阻塞项（无/具体描述 + 建议）
```

## 二、验收标准话术

### 2.1 功能验收标准

**场景**：明确功能完成的标准。

**话术模板**：

```
【功能验收标准】
1. 功能完整性：[具体功能点]必须全部实现，无遗漏
2. 功能正确性：[具体功能点]必须按预期工作，无逻辑错误
3. 功能稳定性：[具体功能点]必须稳定运行，无崩溃或异常

【技术验收标准】
1. 代码质量：符合项目编码规范，无明显代码异味
2. 测试覆盖：新增/变更逻辑必须有单元测试，覆盖率≥80%
3. 性能指标：[具体性能指标]必须满足要求

【工程化验收标准】
1. 日志规范：关键路径、错误分支有结构化日志
2. 错误处理：对外边界失败可观测、可诊断
3. 文档更新：相关文档必须同步更新

【验收流程】
1. 开发自检：开发者完成自检，填写自检报告
2. 代码审查：Reviewer进行独立代码审查
3. 功能测试：测试工程师执行功能测试
4. 验收确认：产品经理确认功能符合需求
```

### 2.2 代码质量验收标准

**场景**：明确代码质量的要求。

**话术模板**：

```
【代码质量要求】
1. 可读性：代码清晰易懂，命名规范，注释适当
2. 可维护性：模块职责单一，耦合度低，易于扩展
3. 可测试性：代码易于测试，依赖可注入，边界清晰

【具体指标】
1. 圈复杂度：单个函数≤10
2. 代码重复率：≤5%
3. 测试覆盖率：≥80%
4. 静态分析：无高危警告

【禁止行为】
1. 禁止硬编码敏感信息
2. 禁止使用已废弃的API
3. 禁止忽略错误处理
4. 禁止编写不可测试的代码
```

## 三、进度跟进话术

### 3.1 进度同步请求

**场景**：请求技术负责人同步进度。

**话术模板**：

```
【进度同步请求】
请提供以下信息：

1. 当前状态：已完成/进行中/阻塞项
2. 范围确认：本轮交付包含什么、不包含什么
3. 风险与权衡：已识别风险、采取的缓解措施
4. 验收口径：将用哪些验证命令/测试证明完成
5. 下一步：接下来要做什么，是否需要确认

【具体问题】
1. 是否有技术难点需要协调？
2. 是否有资源需求需要支持？
3. 是否有时间风险需要预警？
4. 是否有范围变更需要确认？
```

### 3.2 里程碑检查

3. 是否有遗留问题需要解决？
4. 是否需要调整后续计划？

【验收要求】
1. 功能验收：[具体功能点]必须全部实现
2. 质量验收：[具体质量指标]必须满足
3. 文档验收：[具体文档]必须同步更新
4. 测试验收：[具体测试]必须通过
```

## 七、沟通原则总结

### 7.1 专业沟通原则

1. **明确性**：需求描述清晰明确，无歧义
2. **可验证性**：验收标准可验证，可衡量
3. **完整性**：信息完整，无遗漏
4. **及时性**：沟通及时，不拖延
5. **尊重性**：尊重技术专业性，不越界指挥

### 7.2 避免的沟通方式

1. **模糊描述**："优化一下代码"、"尽量完成"
2. **过度干预**：具体技术实现细节的指挥
3. **缺乏标准**：没有明确的验收标准
4. **信息不全**：关键信息缺失
5. **时机不当**：在不合适的时机沟通

### 7.3 有效沟通技巧

1. **结构化表达**：使用模板，逻辑清晰
2. **数据支撑**：用数据和事实说话
3. **聚焦目标**：始终围绕目标沟通
4. **尊重专业**：尊重技术负责人的专业判断
5. **及时反馈**：及时给予反馈和确认

## 八、附录：常用术语表

| 术语 | 定义 | 示例 |
|------|------|------|
| WU | Work Unit，工作单元 | WU-01：实现Coder角色基础框架 |
| Coder | 资深开发者角色 | 对代码类WU负完整交付责任 |
| Implementer | 轻量执行者角色 | 执行文档/模板/纯配置等轻量WU |
| Reviewer | 独立审查者角色 | 独立code review，只读 |
| Leader | 技术主管/编排者角色 | 与用户交互、拆WU、派发、整合、验证 |
| self_check | 开发者自检 | PASS/FAIL，硬门槛 |
| Done criteria | 完成标准 | 条目化，可勾选 |
| wu_type | WU类型 | feature, bugfix, refactor, docs等 |
| wu_skills | WU技能要求 | plan 可写 auto；派发 prompt 须抄 SKILL 路径 |
| agent_role | 角色标识 | coder, implementer, reviewer等 |
