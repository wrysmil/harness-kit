# Harness-Kit 提示词精简原因分析

> 分支: `feat/prompt-minification`
> 分析日期: 2026-08-31

## 一、routing.md 精简原因

### 精简点 1：平台原生 plan 工具段落（原 27 行 → 精简 15 行）

**精简原因：**

| 原因类别 | 具体说明 |
|---------|---------|
| **信息冗余** | "会把 plan 写到平台私有目录"、"完全绕过"等表述重复强调同一事实 |
| **路径细节过详** | `~/.claude/plans/`、`~/.claude/` 等路径对 AI 来说不需要记住 |
| **修复步骤重复** | "补 Harness FM（`route: ...`）"等细节应简化，引用外部文件即可 |
| **违反 DRY** | "Plan 产物"等概念在其他章节已多次出现，无需重复解释 |

**精简依据：**
- Prompt 是给 AI 看的，AI 能理解抽象指令，无需过度展开
- 具体修复命令应交给工具/脚本，而不是写在 prompt 里
- 核心信息只有三点：禁止什么、怎么走 Harness、出问题怎么救

---

### 精简点 2：路由表合并（原 25 行 → 精简 14 行）

**精简原因：**

| 原因类别 | 具体说明 |
|---------|---------|
| **信息过载** | 每行都有 Cursor/Claude 绑定说明，但 Claude Code 运行时不需要区分平台 |
| **违反抽象层次** | 路由表是决策用的，应该简洁；平台绑定是实现细节，应该下沉 |
| **维护成本高** | 每个平台更新都要改路由表，容易不一致 |
| **违反单一职责** | routing.md 应该只定义路由规则，不应该包含平台绑定细节 |

**精简依据：**
- 路由表的核心价值是"什么任务走什么 route"，不是"在哪个平台怎么走"
- 平台绑定是适配器职责，应通过 `bindings.md` 解耦
- AI 执行时先判定 route，再按 route 加载对应 skill，不需要在路由表里预填平台信息

---

### 精简点 3：按判定加载表格压缩（原 22 行 → 精简 12 行）

**精简原因：**

| 原因类别 | 具体说明 |
|---------|---------|
| **路径冗余** | 每个判定都写完整路径 `.ai-runtime-artifacts/specs/...`，AI 已知上下文 |
| **步骤过于详细** | "① → ② → ③" 的顺序对简单任务过于繁琐 |
| **违反分层原则** | 判定与加载顺序是"知识"，不是"操作步骤" |
| **信息重复** | 与路由表中的 skill 引用大量重复 |

**精简依据：**
- AI 加载 skill 是按需行为，不是机械的"第①步第②步"
- 表格化表达更适合做快速查表，不需要知道每个文件的完整路径
- 引用 `artifacts.md` 等文件时，应该信任 AI 会按需读取，而不是列出所有文件

---

### 精简点 4：干预语句精简（原 10 行 → 精简 4 行）

**精简原因：**

| 原因类别 | 具体说明 |
|---------|---------|
| **文字过长** | 每个干预语句都写成完整句子，实际使用时只是复制粘贴 |
| **缺乏结构** | 没有分类，场景和干预语句混在一起 |
| **违反原子性** | "请先读取 CLAUDE.md 和 routing.md" 这种干预语句太长，不够原子 |
| **复用性差** | 每次干预都要重新组织语言 |

**精简依据：**
- 干预语句本质上是"模板"，应该简洁明了
- AI 在收到干预时需要快速理解该做什么，不需要解释为什么
- 表格化更适合快速匹配场景

## 二、verification-before-completion 精简原因

### 精简点 1：Rationalization Prevention 表格精简（原 15 行 → 精简 8 行）

**精简原因：**

| 原因类别 | 具体说明 |
|---------|---------|
| **借口表达多样化** | "Should work now" / "I'm confident" 说的是同一件事：信任而非验证 |
| **违反抽象层次** | 每个借口单独一行，但核心逻辑只有"信任≠验证" |
| **信息密度低** | 表格占用空间大，但信息量少 |
| **维护成本高** | 新增借口要加一行，表格越来越长 |

**精简依据：**
- Rationalization 是心理学现象，同类借口可以合并
- AI 需要知道的是"什么思维模式是错的"，不是记住所有可能的说法
- 用 `/` 连接等价表达，节省空间且更易记忆

---

### 精简点 2：Key Patterns 精简（原 40 行 → 精简 15 行）

**精简原因：**

| 原因类别 | 具体说明 |
|---------|---------|
| **代码块占用大量空间** | 每个场景都有完整的代码示例，但示例是解释性的而非必需 |
| **重复强调核心** | "✅ 正确 ❌ 错误" 的对比在多个场景中重复 |
| **违反图表原则** | 表格比代码块更适合做对比 |
| **信息密度低** | 40 行只传达了 6 个场景的核心 |

**精简依据：**
- AI 理解"Run command → See 0 failures"的模式，不需要完整代码
- 代码示例对于 prompt 来说太大，会稀释核心信息
- 表格可以更紧凑地表达同样的信息

---

### 精简点 3：Why This Matters 整段删除（原 10 行）

**精简原因：**

| 原因类别 | 具体说明 |
|---------|---------|
| **故事性内容** | "from 24 failure memories" 是叙事，不是指令 |
| **信息未经核实** | "your human partner said..." 无法验证真实性 |
| **违反 prompt engineering** | Prompt 应该高效传递知识，不是讲故事 |
| **可删除不影响功能** | 删除后 skill 仍然完整可用 |

**精简依据：**
- Prompt 的读者是 AI，AI 不需要"为什么"只需要"做什么"
- 故事性内容适合放在文档/博客，不适合放在 skill 定义里
- "Honesty is a core value" 这种价值观宣示对 AI 没有实际指导意义

---

### 精简点 4：When To Apply 精简（原 16 行 → 精简 8 行）

**精简原因：**

| 原因类别 | 具体说明 |
|---------|---------|
| **"任何变化"重复** | "ANY variation of success"、"ANY expression of satisfaction" 等重复表达 |
| **规则适用范围的解释冗余** | "Exact phrases / Paraphrases and synonyms" 不需要列出 |
| **信息重复** | "Committing, PR creation, task completion" 与 Common Failures 表格重复 |
| **违反简洁原则** | 8 行能说清楚的不需要 16 行 |

**精简依据：**
- AI 能理解"任何变化"这个概念，不需要列举所有变化类型
- 规则适用范围是常识，不需要明确说明"包括同义改写"
- 保留核心的"什么时候用"即可

## 三、shipping-and-launch 精简原因

### 精简点 1：Pre-Launch Checklist 外置（原 56 行 → 引用 reference）

**精简原因：**

| 原因类别 | 具体说明 |
|---------|---------|
| **违反 DRY 原则** | 代码质量、安全、性能等 checklist 与 `references/` 目录大量重复 |
| **维护成本高** | 两处都要更新，容易不一致 |
| **信息过时风险** | checklist 是动态的，单点维护更安全 |
| **违反单一职责** | SKILL.md 应该定义流程，不应该包含详细 checklist |

**精简依据：**
- `references/` 目录是专门的参考文件，应该成为唯一真相源
- Skill 文件是"如何做"，参考文件是"做什么检查"，职责分离
- 外置后 skill 文件更聚焦在流程和决策上

---

### 精简点 2：Feature Flag Strategy 精简（原 35 行 → 精简 15 行）

**精简原因：**

| 原因类别 | 具体说明 |
|---------|---------|
| **代码示例过长** | 完整的 TypeScript 示例占用 15+ 行 |
| **lifecycle 说明重复** | "flag OFF → team/beta → gradual → monitor → cleanup" 重复出现 |
| **Rules 部分冗余** | "Don't nest feature flags" 是常识，不需要解释原因 |
| **信息密度低** | 35 行只传达了 5 个 lifecycle 阶段和 4 条规则 |

**精简依据：**
- TypeScript 示例对理解 feature flag 概念不是必需的
- AI 理解"分阶段发布"的概念即可，不需要具体代码
- 规则应该精简到最核心的几条

---

### 精简点 3：Staged Rollout 精简（原 60 行 → 精简 25 行）

**精简原因：**

| 原因类别 | 具体说明 |

| **阶段数量过多** | 6 个阶段过于细分，可以合并 |

| **重复解释** | "Monitor at each stage" 等解释在多个地方重复 |

**精简依据：**
- AI 能理解抽象的"分阶段"概念，不需要完整的树状图
- 阈值表格可以精简到 3 列（Advance/Hold/Rollback）
- "每阶段监控"是常识，不需要重复说明

## 七、精简原因汇总

### 精简模式统计

| 精简模式 | 出现次数 | 典型案例 |
|---------|---------|---------|
| **违反 DRY 原则** | 4 | Checklist 重复、Review Checklist 重复 |
| **信息冗余** | 6 | 路径过详、借口表达重复 |
| **故事性内容** | 3 | Why This Matters、Real-World Impact |
| **代码示例过长** | 4 | Error Reporting、Feature Flag Strategy |
| **违反分层原则** | 5 | Checklist 放在 skill 里、平台绑定放在路由表 |
| **表格可以更紧凑** | 8 | Rationalization 表格、Red Flags |
| **DOT/复杂格式** | 2 | TDD 流程图、Staged Rollout 树状图 |
| **未经核实的数据** | 2 | Real-World Impact、某些统计数字 |

### 精简原则总结

1. **DRY (Don't Repeat Yourself)**
   - Checklist 等重复内容应外置到 reference 目录
   - Skill 之间引用而非复制

2. **抽象层次正确**
   - 路由表只定义 route，不包含平台绑定
   - Skill 定义流程，不包含详细 checklist
   - Reference 文件包含详细参考信息

3. **信息密度优先**
   - 用表格替代冗长列表
   - 用关键词替代完整句子
   - 用 `/` 合并等价表达

4. **删除故事性内容**
   - "Why This Matters" 类段落
   - 未经核实的数据
   - 个人经历/"24 failure memories"

5. **代码示例最小化**
   - 保留核心模式，不保留完整实现
   - 框架特定代码外置
   - 用伪代码或流程图替代

6. **格式简化**
   - DOT → ASCII
   - 树状图 → 表格
   - 详细 bullet → 简洁列表

## 八、精简决策树

当审查一个 prompt 文件时，按以下问题判断是否需要精简：

```
该内容是否：
├── 可以外置到 reference 目录？
│   └── 是 → 改为引用，删除详细描述
├── 是故事性/未经核实的内容？
│   └── 是 → 删除
├── 有代码示例且超过 5 行？
│   └── 是 → 精简为核心模式，引用外部文件
├── 借口/Rationalization 超过 5 行？
│   └── 是 → 合并相似表达
├── 是冗长的表格或列表？
│   └── 是 → 精简为紧凑格式
├── 违反 DRY（与其他文件重复）？
```

| 检查项 | 问题 |

| **可读性** | AI 能快速理解吗？ |
